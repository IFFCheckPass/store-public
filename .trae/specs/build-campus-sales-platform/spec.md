# 校园商品销售平台（三端）Spec

## Why
为校园场景提供一个可自助下单、集中生产打包、分级管理的商品销售网站。当前没有支付接口，需要通过“收款码 + 支付截图 + 本地 OCR 识别单号”的方式完成闭环，并以赠货码支持免支付订单。

## What Changes
- 新建 Node 全栈应用：Express 服务 + 内置 `node:sqlite` 数据库 + 原生 ES Module 前端（无需构建），提供用户端 / 生产端 / 管理端三套界面。
- 建立统一账号与权限体系：管理端（最高权限 `super_admin` > 普通管理员 `admin`）> 生产端（内部/外部）> 用户端；生产端与管理端使用“用户名 + 学号 + 密码”三要素登录。
- 用户端支持商品规格/颜色切换与浏览图、购物车、结算信息（收货班级、配送方式、建议时间段、QQ/微信/电话）、微信/支付宝扫码支付示例、支付截图上传与本地 OCR 单号识别、赠货码免支付、订单查询。
- 生产端拆分为外部生产（按单项商品接单并上报生产情况）与内部生产（按订单汇总商品信息，负责打包配送并上报）。
- 管理端支持账号管理、订单查看与检索、支付核验、赠货码生成、多最高权限账号审批删除订单、审计日志。
- 删除订单必须由至少 2 个不同的最高权限账号确认后才生效（软删除归档）。
- 不涉及真实支付、真实物流接口；OCR 为浏览器端 Tesseract.js 本地识别，识别结果允许人工校正。

## Impact
- Affected specs: 新增「校园商品销售」能力域（用户端购物、生产协同、运营管理）。
- Affected code: 全新目录 `server/`（API、数据库、认证）、`public/`（三端前端）、`scripts/`（种子与冒烟测试）、根目录 `package.json`。

## ADDED Requirements

### Requirement: 三端与角色权限
系统 SHALL 提供用户端、生产端、管理端三个入口，并按角色隔离权限：`super_admin` > `admin` > `prod_internal` / `prod_external` > `user / guest`。

#### Scenario: 越权访问被拒绝
- **WHEN** 未登录用户或角色不足的账号访问生产端/管理端 API
- **THEN** 服务端返回 401/403，前端引导至对应登录页

#### Scenario: 生产端与管理端三要素登录
- **WHEN** 账号输入正确的用户名、学号、密码
- **THEN** 登录成功并签发会话令牌（HttpOnly Cookie），进入对应工作台
- **AND WHEN** 任一项不匹配或账号被禁用
- **THEN** 登录失败并提示具体错误

### Requirement: 用户端登录与订单查询
用户端 SHALL 默认免登录浏览与加购；仅在下单或查询订单时要求以“姓名 + 班级 + 座号”登录，系统预留学号字段用于特定场景（如领取核验）。

#### Scenario: 凭预留信息查询订单
- **WHEN** 用户使用下单时的姓名、班级、座号登录后进入“我的订单”
- **THEN** 仅展示与该身份匹配的订单及实时状态
- **AND WHEN** 姓名/班级/座号与订单不匹配
- **THEN** 查询结果为空并提示信息不一致

### Requirement: 商品浏览与规格颜色选择
用户端 SHALL 展示商品列表与详情，支持选择规格（含价格差）和颜色，并同步切换对应颜色的浏览图；选择结果影响购物车条目与下单金额。

#### Scenario: 切换颜色查看浏览图
- **WHEN** 用户在详情页选择某颜色
- **THEN** 主图切换为该颜色的浏览图，缩略图高亮同步更新

#### Scenario: 同商品不同规格/颜色独立成条目
- **WHEN** 用户将同一商品的不同规格或颜色加入购物车
- **THEN** 购物车生成独立条目，数量可增减、可删除，合计金额实时更新

### Requirement: 结算信息与下单
结算页 SHALL 收集收货班级、配送方式（送货到班/自提点）、建议时间段（白天课间、午间、傍晚、晚自习间）、联系方式（QQ/微信/电话，含号码）、备注，并校验必填项与手机号格式。

#### Scenario: 信息不完整无法下单
- **WHEN** 缺少收货班级、时间段或联系方式
- **THEN** 阻止提交并在对应字段提示

#### Scenario: 选择支付方式
- **WHEN** 用户选择微信或支付宝并提交订单
- **THEN** 创建状态为「待付款」的订单，弹出支付引导（操作示例 + 对应收款二维码 + 上传支付成功截图）

### Requirement: 支付截图识别与核验
系统 SHALL 支持上传支付成功截图，在浏览器本地使用 OCR 识别候选支付单号并供用户确认/修正；提交后订单进入「待核验」，由管理端核验通过后进入「已付款」。

#### Scenario: OCR 自动带出单号
- **WHEN** 用户上传清晰支付截图
- **THEN** 系统自动填充识别到的候选单号（如 18–32 位数字串），用户可修改后提交
- **AND WHEN** 识别失败
- **THEN** 提示手动填写单号，仍可提交截图

#### Scenario: 管理端核验
- **WHEN** 管理员在收款核验队列通过某笔支付
- **THEN** 订单状态变为「已付款」并进入生产流程
- **AND WHEN** 管理员驳回并填写原因
- **THEN** 订单回到「待付款」，用户可见驳回原因并可重新上传

### Requirement: 赠货码
最高权限管理员 SHALL 能生成赠货码（可设使用次数、有效期、启停），用户在结算时填入有效赠货码则该订单跳过支付流程，直接标记为「已付款（赠货）」，并核销一次使用次数。

#### Scenario: 使用赠货码下单
- **WHEN** 用户在结算时输入有效且未用尽的赠货码
- **THEN** 订单跳过支付与截图环节，状态直接为「已付款」，赠货码已用次数 +1

#### Scenario: 无效或过期赠货码
- **WHEN** 用户输入不存在、已停用、已过期或已用尽的赠货码
- **THEN** 系统拒绝并给出对应原因

### Requirement: 生产端（外部 / 内部）
系统 SHALL 为外部生产端提供按单项商品（规格/颜色/数量）的待生产任务列表与状态上报（待接单→已接单→生产中→已完成 / 异常）；为内部生产端提供按订单聚合的商品清点与打包配送任务，并上报状态（待打包→打包中→已打包→配送中→已送达 / 异常）。

#### Scenario: 外部生产接单生产
- **WHEN** 外部生产账号接单并更新为「生产中」「已完成」并填写说明
- **THEN** 任务状态与时间线持久化，管理端订单详情可见进度

#### Scenario: 内部生产打包配送
- **WHEN** 内部生产账号打开某已付款订单的打包任务
- **THEN** 可看到收货班级、时间段、联系方式与全部商品明细，并可逐单更新打包/配送状态
- **AND WHEN** 状态更新为「已送达」
- **THEN** 订单状态同步为「已完成」

### Requirement: 管理端账号与订单管理
管理端 SHALL 支持账号列表、新建、编辑、重置密码、启用/禁用、角色分配（仅最高权限可写）；支持全量订单检索（状态、班级、关键词、日期）与详情查看，展示支付截图、OCR 单号、生产与配送进度。

#### Scenario: 普通管理员只读账号
- **WHEN** 普通管理员尝试新增/修改账号或分配角色
- **THEN** 系统拒绝（403），前端不展示写入入口

#### Scenario: 查看订单全链路
- **WHEN** 管理员打开订单详情
- **THEN** 可看到商品明细、支付方式与截图、支付单号、赠货码、外部生产任务、内部打包与配送时间线

### Requirement: 多管理员确认删除订单
系统 SHALL 要求删除订单前发起删除申请，并由至少 2 个不同的最高权限账号确认后才执行软删除；申请人本人若为最高权限账号，其确认可计入但不允许重复确认同一申请。

#### Scenario: 审批未达阈值
- **WHEN** 删除申请仅有 1 个最高权限账号确认
- **THEN** 订单保持可见，申请状态为「待审批」，展示所需/已有确认数

#### Scenario: 审批通过删除
- **WHEN** 第 2 个不同的最高权限账号确认
- **THEN** 订单被软删除（归档，不再出现在常规列表），写入审计日志，关联生产任务停止流转

### Requirement: 审计与数据一致性
系统 SHALL 记录关键操作审计日志（登录、账号变更、支付核验、赠货码生成/核销、订单删除审批），并对库存、支付金额、赠货码次数等使用事务保证一致。

#### Scenario: 下单扣减库存
- **WHEN** 订单创建成功
- **THEN** 对应商品库存按数量扣减；库存不足时整单失败且不产生订单

## 技术方案（实现约定）
- 后端：Node 24 + Express 5 + 内置 `node:sqlite`（`DatabaseSync`），会话使用 `jose` 签发 JWT 并写入 HttpOnly Cookie；密码使用 `node:crypto` scrypt 加盐哈希。
- 前端：原生 ES Modules + Hash 路由的单页应用，三端共用设计系统，无构建步骤；样式采用校园清新明亮风格（浅色底、青绿主色、橙色强调、卡片化）。
- OCR：`tesseract.js` 浏览器端识别，优先使用本地 vendored 资源，失败时降级为手动填写单号（人工校正始终可用）。
- 图片：商品颜色浏览图走统一图片生成服务，加载失败时降级为本地 SVG 占位图；支付二维码使用本地生成的示例图。
- 数据库表：`users`（C 端档案）、`staff`（生产/管理账号）、`products`、`orders`、`order_items`、`payments`、`gift_codes`、`gift_code_usages`、`production_tasks`、`task_events`、`order_deletion_requests`、`order_deletion_approvals`、`audit_logs`。
- 订单状态：`pending_payment` → `pending_review` → `paid` → `producing` → `packing` → `delivering` → `completed`；另有 `cancelled`、`deleted`。
- 运行方式：`npm install && npm start`，默认端口 3000（可用 `PORT` 覆盖），首次启动自动建表并写入演示种子数据。
